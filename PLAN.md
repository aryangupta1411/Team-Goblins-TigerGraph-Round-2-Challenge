## 1. What we are actually being asked to build

### 1.1 The one-paragraph version

Load six months of anonymised card transactions (IEEE-CIS / Vesta, re-cut by TigerGraph) into a TigerGraph graph, then build an **AI agent that takes an alert from a case pack, investigates it through the graph, decides what kind of fraud it is (if any), how far the fraud goes, and what the bank should do next under a written Fraud Policy**, asks for more evidence when the policy says so, explains itself, and writes its case back into the graph so later investigations can retrieve it. Run it on 20 exam cases and submit one JSON answer file per case, a demo video, a blog post, and a social post.

|---|---|---|---|

### 1.3 What the answer key rewards (from the README, not guesses)

- **Half the 20 cases are legitimate.** An agent that blocks everything scores badly. `uncertain` is a valid verdict and earns full credit on ambiguous cases *provided the actions follow R1 and R8*.
- **`fraud_probability` is scored for calibration**, not for matching the model's risk score. The risk score is "often wrong in both directions".
- **Pattern identification** across `card_testing`, `card_not_present_fraud`, `card_not_present_new_device`, `out_of_region_use`, `account_takeover`, `undocumented` (with a free-text `pattern_description`, explicitly scored) and `none`.
- **Scope of the episode**: `affected_txn_ids`, `first_suspicious_txn_id`, `exposure_usd` (sum of absolute amounts), `connected_card_ids`, `connected_device_profiles`.
- **Case vs. report**: deciding between "case only" and "case plus SAR" is part of the next-best-action score. Only 397 of 4,665 historical fraud cases filed a report.
- **Actions must change when evidence arrives**: `next_best_actions.initial` (before any evidence request) vs `final` (after the *assumed* customer/analyst reply), with `what_changed`.
- **Stopping**: stop at probability ≥ 0.85 or ≤ 0.15 with two independent pieces of evidence, or when a verification settles it, or when further steps would not change the decision. Both over-investigating and under-investigating are marked down.
- **Every ID must exist in the dataset.** Made-up IDs score zero. `similar_prior_cases` must be real `CC-xxxx` ids.
- **Explain with rule citations** (R1–R10, 3a) and typed evidence (`graph` / `document` / `customer` / `external`, each with a `ref` and `entity_ids`).

### 1.4 The policy in one table (Fraud Policy v1.0, verbatim identifiers)

| Route | Actions |
|---|---|
| `auto` (agent may execute) | `ALLOW_TRANSACTION`, `MONITOR_CARD`, `MONITOR_CONNECTED_CARDS`, `WARN_CUSTOMER`, `VERIFY_WITH_CUSTOMER`, `STEP_UP_AUTH`, `GENERATE_REPORT`, `CREATE_CASE`, `ESCALATE_TO_ANALYST`, `CLOSE_NO_FRAUD` |
| `L1` (team lead) | `DECLINE_TRANSACTION`; `BLOCK_CARD` when exposure ≤ $2,500 |
| `L2` (fraud manager) | `BLOCK_CARD` when exposure > $2,500; `BLOCK_ALL_CARDS` always; `FILE_REPORT` always |

| Rule | Trigger | Required recommendation |
|---|---|---|
| R1 | single signal (incl. risk score alone) and probability < 0.70 | `VERIFY_WITH_CUSTOMER` or `STEP_UP_AUTH` before any block |
| R2 | customer denies | `BLOCK_CARD` + `CREATE_CASE`; add `FILE_REPORT` if exposure > $1,000 or shared device / other card's fraud |
| R3 | customer confirms | `CLOSE_NO_FRAUD`, note confirmation |
| R4 | no reply in 24 h | `MONITOR_CARD` + `DECLINE_TRANSACTION`; escalate if exposure > $500 |
| R5 | card testing (≥3 small online auths in 1 h then a larger purchase) | `DECLINE_TRANSACTION` + `STEP_UP_AUTH`; `BLOCK_CARD` if a > $100 purchase already cleared |
| R6 | shared origin (device profile / region / recipient email across several cards' fraud in one window) | name the shared element; `CREATE_CASE` + `FILE_REPORT` + `MONITOR_CONNECTED_CARDS` for every sharing card |
| R7 | disputed but matches the customer's own recurring pattern | `CREATE_CASE` + `VERIFY_WITH_CUSTOMER` + `WARN_CUSTOMER`; do **not** block |
| R8 | verdict `uncertain` and exposure > $500, or conflicting evidence | `ESCALATE_TO_ANALYST` |
| R9 | fits no known pattern but shows coordinated/repeated abuse across customers | `CREATE_CASE` + `FILE_REPORT` + `ESCALATE_TO_ANALYST`; describe the pattern in own words |
| R10 | never `BLOCK_ALL_CARDS` unless ≥2 of the customer's cards show confirmed fraud or credentials confirmed compromised | — |
| 3a | open a case at probability ≥ 0.30, whenever evidence is requested, or on any customer dispute; file a SAR only when fraud is confirmed/strongly suspected **and** (exposure > $1,000 **or** shared device/region/other-customer fraud **or** coordinated/undocumented) | `CREATE_CASE` / `FILE_REPORT` |

### 1.5 Judging weights and what each one really tests

| Criterion | Weight | What it tests in practice |
|---|---|---|
| Investigation accuracy | 25% | pattern, verdict, episode scope, connected cards/devices, prior cases retrieved |
| Next best action | 25% | correct action set + route, R1 before blocks, case-vs-SAR, initial → final change, stop rule |
| Case summary & explainability | 10% | evidence objects with refs, rule citations, readable summary, SAR narrative that stands alone |
| Agentic design & engineering | 15% | phases, tool use through MCP, policy gate, memory, permissions, run logging |
| Innovation | 15% | graph algorithms for rings, GraphRAG grounding, memory that visibly helps, monitoring mode |
| Demo | 10% | one ambiguous case walked end to end with the recommendation visibly changing; one ring case |

### 2.2 Facts that change the design

1. **There is no `card_id` column.** It must be derived. The rule that reproduces 100 % of the 14,975 labelled (transaction → card) pairs: `card_id = customer_id + "-K" + dense_rank(card6 among the customer's distinct card6 values, ordered lexically with NULL first)`. This yields 14,317 cards (12,793 customers with one card, 756 with two, 4 with three). `customer_id` is a strict bijection with `card1`. Any other derivation (card2..card6 tuple, first-seen order) matches only 34–38 % and would silently invalidate every card-level answer.
2. **DeviceProfile id** = `DeviceInfo | id_30 | id_31 | id_33` joined with `" | "` (the README's own format; missing parts rendered as the literal `NULL`). 9,705 usable profiles; 3,648 identity rows are all-NULL (no device edge). Profiles such as `Windows | NULL | chrome 66.0 | NULL` are shared by 60–840 cards and are **too generic** to be "shared device" evidence — but profile strength matters only for shared-origin evidence, never for the pattern label (section 4.1). The ring profile is used by **52 cards all-time**, so a strength rule must not cap below that; and plain connected-components over shared devices produces a 5,080-card blob, so ring membership is profile-centric.
3. **`ts` = 2016-07-02 00:00:00 + `TransactionDT` seconds** exactly, so no epoch guessing. 157 same-second ties within a card: `NEXT` edges need a `TransactionID` tiebreak.
4. **Time-box evidence to `ts <= opened_at`.** Every one of the 14,955 closed-case transactions precedes its case's `opened_at`; exam `opened_at` = flagged `ts` + 1..6 whole hours. Transactions after `opened_at` exist for every exam case (up to 289 in 7 days for HHG-018) and must not enter `affected_txn_ids` / `exposure_usd`; they are reported as a monitoring note. `connected_card_ids` for a ring, by contrast, cover the whole wave (the closed ring cases include post-open cards).
5. **The closed-case history is a rulebook in disguise.** `actions_taken` has only three combinations: `CREATE_CASE|BLOCK_CARD` (4,268), `CREATE_CASE|BLOCK_CARD|FILE_REPORT` (397), `VERIFY_WITH_CUSTOMER|CLOSE_NO_FRAUD` (900). `report_filed = Yes` exactly when exposure > $1,000 **or** the case belongs to the shared-device ring (policy 3a applied mechanically). All cleared cases are risk-score alerts (score 0.81–0.99) with three note templates: *confirmed travel to the billing region* (716), *confirmed the purchase from a new phone* (158), *confirmed an unusual amount consistent with stated intent* (26). All fraud cases were customer-reported; **no customer denial was ever cleared**. There are **no** historical examples of `DECLINE_TRANSACTION`, `STEP_UP_AUTH`, `MONITOR_*`, `ESCALATE_TO_ANALYST`, or an `uncertain` outcome — those must come from the policy text, not from retrieval.
6. **The closed cases are the complete Jul–Oct fraud labels**, and their pattern labels follow a mechanical convention (section 4.1): mixed channel → account takeover; all in-person in the card's modal region → account takeover; other in-person → out-of-region; all online with any New member → CNP new device; else CNP. Fraud episodes are chains with ≤ 48 h gaps.
7. **Two undocumented patterns are seeded** (the "small number of rows added" in the README; seeded rows have `ts` seconds == `:00`, a QA aid we never cite as evidence):
   - **Anonymous-proxy device ring**: profile `SM-G935F Build/NRD90M | Android 7.0 | chrome 62.0 for android | 1920x1080` (note the `Build/NRD90M`, the exact dataset string) with `id_23 = IP_PROXY:ANONYMOUS`, all ProductCD C, 114 rows over 52 cards in Aug/Sep/Nov/Dec. Closed cases CC-2649/2971/2985/3035 each list 23 `connected_card_ids` (the whole Aug–Sep wave, including cards first seen after each case opened). **HHG-014 sits on it**: 27 other cards form the Nov–Dec wave, 19 of them active before the case's `opened_at`.
   - **Just-under-$500 burst**: four online purchases of $450–$499.99 within ~40 minutes (CC-3748/3841/3907/4086/4124, all filed, all with empty connected-card lists). **HHG-006 is one** ($478.95, $456.96, $488.04, $482.12 in 30 minutes on a card with two prior online purchases), and 11 more customers show exactly the same shape in Nov–Dec (C00466, C01890, C02265, C03633, C05423, C05766, C05851, C06881, C10751, C10990, C12641) — candidates for the optional monitoring folder. In Jul–Oct the shape also fires on 12 cards with no case, so without a denial it is a strong signal, not proof.
8. **Case memory matters on this exam.** 16 of the 20 exam cards already have closed cases; HHG-007's card has 19, HHG-018's has 20, HHG-011's has 4 prior `card_testing` cases. HHG-006/009/014/016 have none.
9. **Closed-case notes are templated** (six templates), so pure embedding similarity returns boilerplate. Similar-case retrieval must be structural first (same card / customer / device profile / region / pattern within a window) and vector second, with amounts and ids masked before embedding.
10. **Channel** is fully determined by `ProductCD` (`W` = in_person, else online). `id_15` (New / Found / Unknown) and `id_23` (proxy type) are the "new device" and "proxy" signals; a transaction with no identity record has an *unknown* device, never a "new" one. **A New device is not by itself a fraud signal in this data** (online New 4.5 % fraud vs 6.8 % for online overall; the cleared "new phone" alerts are New-device ones), yet it is exactly what the label convention keys on once an episode is fraud.

## 3. Architecture and stack decisions

### 3.1 Decisions (with the reasons they were made)

| Decision | Choice | Why | Rejected |
|---|---|---|---|
| Database | **TigerGraph Savanna**, one read-write workspace, size **TG-00** (2 vCPU / 16 GiB / 8 GiB topology, $1/h from free credits), newest **4.2.x** runtime | Vector attributes + `vectorSearch` need 4.2+; free credits; official MCP support via a Database Secret. Community Edition Docker images are amd64-only and TigerGraph says ARM is unsupported; on a 16 GB Apple-Silicon Mac it would compete with the agent for RAM. | CE as primary (fallback recipe only: Rosetta, 10–12 GB Docker memory, `tigergraph/community:4.2.5`). |
| Graph access from the agent | **tigergraph-mcp 1.0.3** over stdio, started by a 15-line launcher that gives the shared connection a 120 s query timeout | Mandatory stack item. `run_installed_query` sends no timeout, so the server's 16 s default applies unless we pre-populate the connection pool with `customizeHeader(timeout=120000)`. | Raw pyTigerGraph from the LLM loop (fails the MCP requirement); Anthropic's server-side MCP connector (needs a public HTTPS URL). |
| Bulk loading, algorithms, embeddings, scorer | **pyTigerGraph 2.0.4** + **DuckDB** + **LightGBM** in offline scripts with explicit timeouts | Loading 590k rows, running WCC / PageRank, and scoring every transaction through the MCP would hit the 16 s and 128 MB limits. DuckDB already exists (`hhgoa.duckdb`, 17 s to build). | tigergraphx (unmaintained, Python < 3.13). |

**Device-profile strength and ring membership (the rule every draft got wrong):** the ring profile is used by **52 cards all-time**, so any all-time cap ≤ 50 silently deletes the ring, while a loose cap makes 112-card profiles "strong" and over-files SARs. `is_strong = DeviceInfo present AND ≥ 3 of the 4 fields populated AND n_cards_alltime ≤ 60 AND 2 ≤ n_cards_30d ≤ 40 in some 30-day window`. Strength governs shared-origin evidence, `connected_card_ids`, `connected_device_profiles` and the 3a shared-device clause (which additionally needs ≥ 2 other confirmed-fraud cards on the profile within ±30 d); it never affects the pattern label. **Connected components are not a ring detector on this data**: WCC over a `SHARES_DEVICE` projection of strong profiles yields one 5,080-card component (hub profiles such as `Windows | Windows 7 | chrome 63.0 | 1920x1080` carry 67 fraud cards and bridge everything), and no fan-out cap or fraud filter separates the ring. So `Card.ring_id` is **profile-centric**: the id of a strong profile on the card's online transactions that has ≥ 2 confirmed-fraud cards, or an anonymous-proxy share ≥ 0.9; `ring_profile(card)` is `device_neighbors` over that profile with proxy share and fraud-case counts. Unit tests assert that the exact string `SM-G935F Build/NRD90M | Android 7.0 | chrome 62.0 for android | 1920x1080` is strong and that `device_neighbors` on it returns 52 all-time cards, 27 other cards in November, and 19 other cards active before HHG-014's `opened_at`. Generic profiles such as `NULL | NULL | chrome 66.0 | NULL` (175 cards) or `Windows | Windows 10 | chrome 63.0 | 1920x1080` (842 cards) are never "shared device" evidence.

Sizing: 590,742 Transaction, 14,317 Card, 13,553 Customer, 9,705 DeviceProfile, ~60 EmailDomain, 332 BillingRegion, 5,565 ClosedCase, ~150 PolicyChunk; ≈ 2.5 M edges. ### 3.7 GraphRAG design (graph first, vectors second)

- **Knowledge layer in the graph**: `PolicyChunk` (policy rule R1–R10 and sections 3a/3b/6 one chunk each; the five README patterns one chunk each; regulatory chunks) linked `ABOUT` their `FraudPattern`; `ClosedCase.note_emb` over template-parsed, masked notes (`pattern | outcome | device | region` prefix, amounts / ids / dates masked); `AgentCase.note_emb` over our own summaries so case N+1 retrieves case N.

The LLM receives a **context pack** (typed evidence bullets with ids, similar cases with outcomes and distances, rule and regulation excerpts with section ids), never raw rows.

## 4. The decision engine and the agent loop

The rubric rewards *defensible* decisions, and the closed cases show the answer key follows conventions, not judgement. So the split is: **deterministic code computes the scorecard, the pattern, the episode, the SAR decision and the admissible actions; the LLM chooses which playbook queries to run, writes evidence claims, summaries, reasons and the SAR narrative, and may move the probability by at most ±0.10 with a cited reason.** Every rule below was checked against the closed cases in DuckDB; the per-case expectations in section 2.3 are provisional until `qa/expectation_sheet.py` regenerates them from the engine on day 5.

### 4.1 What the closed cases taught us (computed on the real files, no Kaggle data)

1. **The closed cases are the complete Jul–Oct fraud labels.** Case transactions are 2.5–4.1 % of each month's rows and 0 % of Nov–Dec; the exam answer key is the same generator over the withheld Nov–Dec labels. **Trigger type determines outcome in history**: 4,665/4,665 fraud cases were customer-reported, 900/900 cleared cases were model alerts. Any calibrator trained at case level would learn that leak, so the scorer is trained on transaction-level labels over all Jul–Oct rows.
2. **Risk score calibration (all Jul–Oct rows):** fraud rate by band `<0.1` 0.5 %, `0.3–0.5` 8 %, `0.5–0.7` 16–19 %, `0.7–0.8` 23 %, `0.8–0.9` 31 %, `0.9+` 41 %; for `risk ≥ 0.8` in-person 56 % vs online 25 %. "Above 0.7 mostly legitimate" is true, but not overwhelmingly.
3. **A "New" device is not a fraud signal here** (online New 4.5 % vs 6.8 % for online overall; the cleared alerts *are* the New-device ones). Found device 9.4 %, anonymous proxy 11.3 %, `protonmail.com` 47 % (n = 60). Amount above the card's prior max 4.5 %; region never seen 1.7 %. A hand-built scorecard from these base rates cannot rank cases; a learned scorer can.
4. **Case-memory scorer (CMS).** LightGBM on the 393 Vesta columns + identity + risk_score + card-history features, trained on Jul–Sep transaction labels, October holdout: **AUC 0.956** (risk score alone 0.866), calibrated bins `<0.05` → 0.7 % fraud, `0.3–0.5` → 46 %, `>0.85` → 78 %. The model file and Nov–Dec scores already exist (`lgb_fraud.txt`, `novdec_scores.parquet`); `etl/cms_train.py` re-trains them and emits `cms_p` into the transaction chunks so the graph is loaded once. Framing, honestly: *memory-informed calibration learned from the bank's own 5,565 closed cases*, exposed as one attribute among many evidence items; the verdict path stays graph-rule driven. Note that the scorer does **not** recognise the two seeded patterns (HHG-006 at 0.02, HHG-014 at 0.08), which is exactly why the detectors below override it.
5. **The generator's pattern convention**, verified on all 4,665 fraud cases: any in-person + any online in the episode → `account_takeover` (230/230); all online with **any** `New` member, regardless of profile strength → `card_not_present_new_device` (1,076/1,076; 439 of them have only generic New profiles); all online, no New → `card_not_present_fraud` (1,404/1,404; 49 have no identity record at all); all in-person and every member in the card's **modal in-person region** (no share threshold: 67 of these cases have modal share < 0.3) → `account_takeover` (944/990); all in-person otherwise → `out_of_region_use` (909/955). `card_testing` (16 cases, 9 cards) are long online runs (mean 27 transactions, up to 30 days) containing ≥ 1 sub-$5 authorisation; the README's R5 shape alone fires on 16 Jul–Oct cards of which only 4 hold a card-testing case, so R5 drives *actions* while the label rule is "all-online chain with ≥ 5 members and ≥ 1 sub-$5 member". `undocumented` = the two seeded shapes.
6. **Episode boundaries:** intra-episode gaps p50 / p90 / p99 = 1.9 / 27.9 / 46.3 h; the gap between consecutive episodes on a card has p1 = 48.6 h. So an episode is the **≤ 48 h-gap chain** on the card. 55 % of episodes are one transaction, and 1,132 episodes have legitimate transactions interleaved, so "everything in the window" is wrong. Chain membership by `cms_p ≥ 0.30` or signature match recovers October episodes with mean Jaccard 0.86 (flagged-only: 0.70). Home-region members occur inside out-of-region episodes and must not be filtered out.
7. **SAR rule:** `report_filed = exposure > $1,000 OR case is in the device ring` on 4,665/4,665 fraud cases; only 397 filed. Ring cases list **every other card of the wave, including cards whose first ring activity was after the case opened** (CC-2649 lists 23 cards, 4 of them post-open), so `connected_card_ids` is wave-scoped while `affected_txn_ids` stays time-boxed.
8. **Recurring charges (R7):** amount recurrence alone is a card-volume artefact (a $39 price point recurs near-daily on a card doing 40 transactions a day), so R7 needs amount **and** product **and** place **and** cadence, and the scorer must agree.

### 4.4 Pattern rule, episode rule, exposure, connected entities (code)

- **Pattern** (detectors first, then the convention): ring-profile hit or ≥ 4 × $450–499.99 online within 40 min → `undocumented`; all-online chain with ≥ 5 members and ≥ 1 sub-$5 member → `card_testing`; mixed channel in the chain → `account_takeover`; all in-person with every member in the modal in-person region (computed at `ts ≤ opened_at`) → `account_takeover`, other in-person → `out_of_region_use`; all online with **any** New member → `card_not_present_new_device`; else `card_not_present_fraud`. Verdict `legitimate` → `none`. A unit test replays the 4,665 fraud cases through the rule (target ≥ 95 %).
- **Episode** (`affected_txn_ids`): transactions on the case's card with `ts ≤ opened_at` in the ≤ 48 h-gap chain containing the flagged transaction, whose `cms_p ≥ 0.30` **or** signature match (same strong profile, or same email + product with amount within 5 % inside 2 h) **or** pattern membership (all ring-profile transactions on the card; all burst members; the card-testing chain). Home-region members are allowed inside an out-of-region episode. Always includes the flagged. `uncertain` → flagged plus members with `cms_p ≥ 0.5` (the rest of the candidate chain is named in evidence). `legitimate` → `[]`, `first_suspicious_txn_id = ""`, exposure 0.
- `exposure_usd = round(Σ|amt|, 2)`; `first_suspicious_txn_id` = earliest affected; `activity_dates` = `YYYY-MM-DD` strings of min / max affected `ts`, `[]` when no SAR.
- `connected_card_ids`: for a ring, every other card on the strong profile in the same wave (closed-case convention), with pre-open cards marked in evidence; otherwise other cards with fraud-episode transactions on the same strong profile within ±30 d, or `CONNECTED_TO` cards of a retrieved ring case; burst look-alikes are **not** connected (closed burst cases had empty lists) — they are named in `pattern_description`.
- `connected_device_profiles`: strong profiles only, exact 4-field strings; `sar.subjects` lists the customer, cards and the device strings named in the narrative.
- `similar_prior_cases`: 3–6 `CC-` ids from the retriever. Agent-written cases are **never** placed in `entity_ids` or `ref` (README: every id must exist in the dataset); they are named in the claim text and summary, cited through `ref: "query:prior_cases_for_customer(...)"`, and stored in the graph as `CASE_SIMILAR_TO` edges. The validator fails hard on an `AC-` id in `entity_ids`.
- **Status**: `open` if a reply is pending or inconclusive; `escalated` if `ESCALATE_TO_ANALYST ∈ final`; else `closed_fraud` / `closed_legitimate`. Invariant: `verdict == uncertain ⇒ status ∈ {escalated, open}` (R8's conflict clause always applies to an uncertain verdict, so cite R8 even when exposure ≤ $500).
- TransactionIDs are emitted as strings; `evidence_requests = []` when nothing was asked; `pattern_description = ""` unless `undocumented`.

### 4.5 Calibrated `fraud_probability`, bands, and the stop rule

`p_engine = clip(logit⁻¹(logit(cal(cms_p)) + Σ adjustments))`, `cal` = isotonic calibration on October out-of-fold predictions; adjustments (capped at ±2.2 total): ring profile → floor 0.90; burst **with a denial** → floor 0.90 (without one, e.g. a monitoring alert, 0.55 and R1 verify); card-testing chain +1.4; **customer denial → floor 0.55** (not a log-odds bump: a bump over a 0.007 prior gives 0.02, which would turn HHG-004 into a "legitimate" file carrying a block); R7 match −1.2; prior cleared alert of the same template on the card −0.5; recent card-testing / CNP case on the card +0.5; strong shared profile with ≥ 2 other fraud cards within ±30 d +1.4; scorer-unreliable flag (card with > 3,000 transactions or `card_seq < 5`) shrinks 30 % toward 0.5. **Conflict override**: when the rulebook builds a chain worth > $500 (mixed-channel spree above the card's prior in-person max, or a New device from a never-seen region) but `cms_p < 0.30`, clamp to [0.30, 0.50], verdict `uncertain`, request `step_up_auth`, escalate under R8.

**Evidence families** (counted in code, used by R1 and the stop rule): (1) card history and baseline, (2) device / ring / shared origin, (3) case memory (prior cases, similar cases, scorer), (4) customer / analyst reply. Documents ground rules, they are not evidence of fraud.

**Bands and actions:** `fraud` when `p ≥ 0.70` (initial = the fraud set; a verification is still asked while `p < 0.85`, cited as §3b / §5 — never as R1, which only applies below 0.70 with one family; the validator lints this); `uncertain` when `0.15 < p < 0.70` (initial = `CREATE_CASE` + `VERIFY_WITH_CUSTOMER` or `STEP_UP_AUTH` + `MONITOR_CARD`, plus `ESCALATE_TO_ANALYST` under R8 when exposure > $500 or evidence conflicts; **never a block in initial**); `legitimate` when `p ≤ 0.15` (aligned with §6 test 1) or after a confirmation (ceiling 0.10) → `CLOSE_NO_FRAUD` (+ `ALLOW_TRANSACTION` for a risk alert); `GENERATE_REPORT` when `p < 0.30` and no case was opened.

**Stop rule (policy §6, checked after P4 and P7):** stop when `p ≥ 0.85` or `≤ 0.15` with ≥ 2 independent families; or a verification response settled it; or `voi.py` shows no admissible request can change the action set. `stop_reason` names the test that fired. Post-evidence: confirmation → ceiling 0.10; denial through a request → +1.1 (floor 0.80 only when a second family already supports fraud); step-up passed → −1.0; failed → +0.7; inconclusive → unchanged.

### 4.6 Evidence-request simulation (deterministic, evidence-driven, logged in `evidence_requests`)

The assumed reply is a function of the **evidence families**, not of the probability alone, so the evidence can disagree with the prior:

| Request | Assumed response |
|---|---|
| `customer_validation` | **confirms** when L ≥ 2 and F ≤ 1 (text drawn from the matching cleared template: travel to the region / new phone / unusual amount intended); **denies** ("did not make these purchases, still has the card") when F ≥ 2; otherwise **no reply within 24 h** → R4 `MONITOR_CARD` + `DECLINE_TRANSACTION` (stated as applying to pending / further authorisations), `ESCALATE_TO_ANALYST` when exposure > $500 or a conflict, status `open`, probability unchanged |
| `step_up_auth` | **passes** when the device is known to the card and F ≤ 1; **fails** when F ≥ 2; otherwise **not completed within the window** → treated as R4 above |
| `analyst_info` | deterministic summary from `device_neighbors` / burst prevalence (e.g. "27 cardholders on this profile in the November wave; 4 closed as undocumented in August–September") |

The "no reply" branch is never *chosen* to decorate a legitimate-leaning exam case; it occurs only when the families are genuinely balanced (HHG-003, 011, 015, 018 are the candidates). R4 is demonstrated in the UI on a replayed closed case if no exam case reaches it. `voi.py` computes `final_if_confirm / deny / no_reply` from the gate; if all three give the same action set the request has zero value of information and is not made. The counterfactual branch is written into `what_changed` and shown in the UI.

### 4.7 Policy gate (`engine/policy.py`, `policy/fraud_policy.yaml`)

Routes: `auto` = the ten auto actions; `L1` = `DECLINE_TRANSACTION`, `BLOCK_CARD` (exposure ≤ $2,500); `L2` = `BLOCK_CARD` (> $2,500), `BLOCK_ALL_CARDS`, `FILE_REPORT`. Rules R1–R10 and 3a encoded as `when / require / forbid / add_if` templates (R1: `p < 0.70` and families < 2 → forbid blocks, require verify or step-up; R2 on a denial once the verdict is fraud, or in `final` after a failed step-up; R3; R4; R5; R6; R7; R8; R9; R10 forbid `BLOCK_ALL_CARDS` unless ≥ 2 cards with confirmed fraud). Case rule: `CREATE_CASE` whenever `p ≥ 0.30`, whenever any evidence is requested, and on every customer dispute. SAR rule: fraud confirmed / strongly suspected **and** (exposure > $1,000 **or** strong shared device with ≥ 2 other confirmed-fraud cards **or** shared region cluster **or** another customer's / card's fraud **or** undocumented / coordinated). Ordering is enforced from the YAML (`CREATE_CASE → verify / step-up → MONITOR_* → DECLINE → BLOCK → FILE_REPORT → ESCALATE → CLOSE`), not by the LLM. `authorize()` executes `auto` actions (recorded as `CaseEvent executed`); `L1` / `L2` are queued to `approvals.sqlite` as `pending` (the answer reflects recommendation, not execution). The LLM's proposed list is checked; violations get one re-prompt, then a deterministic correction logged as `policy_override`.

Invariants asserted by `answer_writer`: `sar.file ⇔ FILE_REPORT ∈ final`; `FILE_REPORT ⇒ CREATE_CASE`; `legitimate ⇒` empty affected, exposure 0, no SAR, `CLOSE_NO_FRAUD ∈ final`, no block anywhere; `BLOCK_CARD ∈ final ⇒ verdict ≠ legitimate`; `uncertain ⇒` no block in `initial` and status `escalated` or `open`; routes match the table; `initial ≠ final ⇒ evidence_requests non-empty` (one-directional); `what_changed == "nothing" ⇔ initial == final`; `pattern_description ≠ "" ⇔ undocumented`; "R1" appears in a reason only when `p < 0.70` and families < 2; `sar.reason` non-empty always (template for the negative case: "3a not met: exposure $X ≤ $1,000; the New profile `…` is used by N cards with no fraud linkage, so it is not a shared-origin signal; no other customer's fraud connected").

### 4.8 SAR narrative

`sar.py` builds a fixed skeleton — S1 typology + internal case id; S2 who (customer, cards, device profile); S3–S5 what / when / how chronologically with dates, amounts, channel, region, device; S6 why unusual vs baseline; S7 prior SAR on the card (from `ClosedCase.report_filed`) and OFAC screening result; S8 actions taken and connected cards monitored — and the LLM writes the prose with 3–5 retrieved FinCEN chunks in context. `validate_sar.py` checks 6–12 sentences, ≥ 1 ISO date and amount, non-decreasing dates, subjects present and existing, `total_amount_usd == exposure_usd`, `activity_dates` = min / max, no "see attached", tabs or tables. Expected filings on the pack: HHG-006 and HHG-014; HHG-015 only if a step-up failure confirms the mixed-channel episode (an assumed failure alone on a 0.008 scorer would be over-filing, so its default is the R4 path with no SAR).

### 4.9 Answer-file validator (before every write)

Schema equal to the README fields with exact enums; every `TransactionID`, card id, `CC-` id, customer id and device-profile string resolved against DuckDB; `entity_ids` extracted by code from tool results; `exposure_usd` recomputed; affected transactions on the case card (or a listed connected card) and `ts ≤ opened_at`; the invariants of 4.7; a lint that no claim, `pattern_description` or narrative cites the ":00 seconds" seeding tell; a lint that numeric claims the validator can parse (counts, amounts, dates) match a re-run of the cited query; a repo lint for Kaggle / IEEE-outcome references.

## 7. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| The answer key does not follow the closed-case conventions (e.g. disputes treated as fraud unconditionally, post-open transactions included, connected cards time-boxed) | accuracy | Follow the evidence-backed conventions; keep `uncertain` + R1 / R8 on the conflict cases (full credit when ambiguous); ask on Discord about `opened_at` bounding and connected-card scope; state the alternative reading in each summary |
| Judges read the LightGBM scorer as "an ML model replacing graph analysis" | agentic design / innovation | Frame it as memory-informed calibration learned from the bank's own closed cases; expose it as one graph attribute among many evidence items with plain-language contributing signals; keep the verdict path graph-rule driven; publish the calibration table |
| Savanna credits run out or the workspace is terminated (amount unpublished; auto-stop locked on; billing transition makes the balance unreliable; no shell, so no server-side export) | no database on demo day | Check the balance on day 0 and apply the credit decision rule; keep auto-stop / auto-start on (brief requirement) and suspend manually as an extra saving; `rebuild.py --from <stage>` from the checked-in chunks and vector files is the disaster-recovery path (timed on day 2); take the one manual backup after day 6; record the demo on day 13 |
| 16 s query timeout through the MCP; 502 on auto-resume | investigations fail mid-case | launcher sets a 120 s timeout (unit-tested); every agent query bounded and profiled on the three largest cards; whole-graph work (bursts, ring hits, look-alikes, WCC) precomputed as attributes; `ensure_awake()` and keep-alive |
| Wrong `card_id` derivation, generic device profiles, mis-quoted ring string, illustrative README ids, agent-case ids in evidence | fields score zero | rule validated on 14,975 pairs and tested in CI; strength rule tested against the exact ring string; validator resolves every id against DuckDB before promotion and fails on `AC-` ids in `entity_ids`; numeric claims re-checked against the cited query |
| A GSQL reserved word in the schema (`Case`) | DDL rejected on day 2 | `AgentCase`; `CREATE VERTEX` smoke test for every name on day 0 |
| WCC over shared devices yields a giant component (verified: 5,080 cards) | ring evidence meaningless | profile-centric ring rule; WCC reported honestly as an experiment |
| The expectation sheet was written by hand and disagreed with the engine on six cases in review | wrong files frozen | `qa/expectation_sheet.py` regenerates it from the engine on day 6; every diff reviewed |
| Over-blocking or over-filing | next-best-action score | denial floor + uncertain band with no initial block; R1 and the SAR rule in code; evidence-driven simulator with a confirm branch; the 30 cleared-as-dispute replays must not be blocked; benchmark distribution reviewed by hand |
| Evidence leakage past `opened_at` | wrong episode scope | `as_of` on every query; validator rejects ids with `ts > opened_at` |
| Two-type `vectorSearch` with a mixed candidate set unverified; index not ready after a write | memory retrieval empty | day-0 smoke test with a two-query fallback; single-call upsert of attributes + vector; index poll before the next case; structural fallback |

## Appendix A. How this plan was produced and what was verified

- Sources read in full: the hackathon brief, the dataset README (policy, answer format, 20 cases), all four data files (downloaded and profiled in DuckDB), and the TigerGraph MCP / Savanna / GSQL algorithm / TigerVector / Anthropic SDK documentation and source (7 research reports, a completeness critic, 4 gap-fill investigations).
- Facts established on the real data: the `card_id` rule (14,975/14,975), the device-profile format and the exact ring string, `ts` = 2016-07-02 + `TransactionDT`, the closed-case action / report conventions, the pattern-label convention (verified on 4,665 cases), the 48 h episode chain, the two seeded patterns and their exam cases, the hand investigation of all 20 exam cases, and the case-memory scorer (October holdout AUC 0.956).
- Design: three independent build plans (score-first, engineering-first, innovation-first) scored by two judges and merged; then three adversarial reviewers (README compliance, technical feasibility, scoring logic) tried to break the merged plan. Their blockers were folded in: the pattern rule ignores profile strength; a denial floors the probability so no dispute can be "legitimate with a block"; uncertain verdicts never carry an initial block; the R7 gate was tightened and its fires logged; HHG-014's actions are final from the start and its connected cards cover the wave; ring membership is profile-centric because WCC on this data produces a 5,080-card component; whole-graph scans became precomputed attributes; the schedule was re-baselined with a day-6 fallback; and several per-case numbers were corrected.
- Still provisional: the per-case expectation sheet (regenerated from the engine on day 6), the Savanna runtime and credit facts (day 0), and the Discord questions above.
